# enclave-exec — the judging core (pre-TEE)

The one genuinely new capability behind the whole workflow: **run a hunter's
exploit against a live target, with a secret flag, and decide PASS/FAIL by
whether the exploit captured the flag.** This is the pre-TEE stand-in for what
will eventually run inside the TEE. Everything else in the payout cycle (escrow,
verdict signing, atomic reveal) already exists — this is the piece that makes the
verdict *real* instead of mocked.

It uses the same Docker mechanism the `hunter-vm/` POC proved, hardened into a
judge:

- the secret flag is generated by the judge (not baked into any image);
- the target runs isolated on a **loopback-only** docker network (`--internal`),
  so a submitted exploit cannot phone home;
- the flag is injected into the target at run time;
- the exploit runs in a separate container with memory/cpu/pid caps and a hard
  timeout, reaching the target only as `target:1337`;
- **only the exploit's stdout is inspected** for the flag — the exploit never
  learns the flag except by actually exploiting the target.

## Try it (on a Docker host — your Linux box)

```bash
# 1. build the target + runtime images (once)
bash enclave-exec/build.sh

# 2. judge the working exploit  -> PASS
node enclave-exec/execute.mjs examples/ret2win/solution/solve.py

# 3. judge the broken exploit   -> FAIL
node enclave-exec/execute.mjs examples/ret2win/solution/solve-broken.py
```

`execute.mjs` prints the exploit's captured output, then `PASS` or `FAIL`. Exit
code: 0 = PASS, 3 = FAIL, 1 = couldn't judge (an execution error).

Because the flag is random per run, a PASS means the exploit genuinely leaked the
freshly-injected secret — it cannot be faked by printing a hard-coded string.

## How this becomes the product

`judge(exploitBytes, { flag })` is exported so the pre-TEE enclave can call it:
the enclave unseals the hunter's exploit, derives the bounty's real flag, calls
`judge`, and signs a PASS/FAIL verdict the chain settles atomically. That
integration is the next increment (see `docs/integration-plan.md`). Moving to the
real TEE later means running this same judging inside a Nitro Enclave with an
in-enclave key — the mechanism is unchanged.

## Tunables (env)
`SCB_TARGET_IMAGE` (default `scb-target`), `SCB_RUNTIME_IMAGE` (`scb-runtime`),
`SCB_TARGET_PORT` (`1337`), `SCB_EXPLOIT_TIMEOUT_S` (`60`), `SCB_DOCKER`
(`docker`).

## POC caveats
Single baked target (ret2win); per-bounty targets pulled from a manifest come
later. The container hardening here is basic (caps, timeout, internal network,
no external egress) but not the full TEE isolation — that is what the TEE phase
adds.
